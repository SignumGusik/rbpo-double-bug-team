# Паспорт проекта

## Общие сведения

**Название команды:** DoubleBug

**Название продукта:** Campus Events

**Коды участников:** `M1`, `M2`

## 1. Назначение

Campus Events - учебный сервис регистрации на мероприятия. Организатор создаёт мероприятие с ограниченным числом мест и
публикует его, участники регистрируются и при необходимости отменяют участие, а организатор получает актуальный список
участников своего мероприятия.

Собственная предметная логика продукта включает соблюдение вместимости мероприятия (число активных регистраций никогда
не превышает число мест, в том числе при одновременных запросах), допустимые переходы мероприятия между состояниями,
правила регистрации и отмены (только для опубликованного мероприятия и до его начала, не более одной активной
регистрации участника на мероприятие) и разграничение доступа к списку участников. В проекте используются только учебные
аккаунты и вымышленные данные.

## 2. Граница продукта

**В продукт входит:**

- аутентификация заранее созданных учебных аккаунтов;
- полномочия Participant и Organizer;
- просмотр опубликованных мероприятий без входа в систему (без персональных данных участников);
- создание мероприятия организатором в состоянии DRAFT;
- редактирование собственного мероприятия, включая изменение вместимости с учётом уже занятых мест;
- публикация мероприятия (DRAFT -> PUBLISHED);
- отмена мероприятия организатором (PUBLISHED -> CANCELLED) с автоматической отменой всех активных регистраций;
- регистрация участника на опубликованное мероприятие при наличии свободных мест;
- отмена участником собственной регистрации до начала мероприятия;
- просмотр участником собственных регистраций;
- просмотр организатором списка участников только своих мероприятий;
- хранение мероприятий, регистраций, учётных записей и журнала значимых изменений;
- регистрация значимых изменений для последующего аудита;
- API-документация и воспроизводимый локальный запуск.

**Внешнее окружение и внешние системы:**

- HTTP-клиент: Swagger UI, curl или другой REST-клиент;
- GitHub как хранилище исходного кода и истории проекта.

Данные хранятся в локальном файле SQLite. Внешние прикладные сервисы и отдельный сервер базы данных для основных
сценариев не требуются.

**Команда сознательно не реализует:**

- список ожидания (возможное расширение после EK1);
- модерацию публикаций мероприятий (возможное расширение после EK1);
- полноценный frontend и мобильное приложение;
- самостоятельную публичную регистрацию аккаунтов и восстановление пароля;
- оплату участия и продажу билетов;
- email- и push-уведомления;
- QR-коды, отметку посещения и чек-ин на входе;
- загрузку файлов и изображений;
- внешние интеграции (календари, карты, социальные сети);
- аналитику, отчётность и отдельную административную панель;
- реальные персональные или чувствительные данные.

## 4. Сквозные сценарии

### Сценарий 1. Создание и публикация мероприятия

- **Участники:** Organizer.
- **Начальное условие:** организатор аутентифицирован; мероприятия ещё нет.
- **Основные действия:** организатор передаёт название, описание, место, дату и время начала и число мест; сервер
  определяет владельца по аутентифицированному контексту и создаёт мероприятие в состоянии DRAFT; организатор проверяет
  карточку и выполняет команду публикации; сервер проверяет, что дата начала в будущем и вместимость положительна, и
  переводит мероприятие в PUBLISHED.
- **Результат:** мероприятие видно в публичном списке, на него можно зарегистрироваться.
- **Какие данные или состояние изменяются:** создаётся мероприятие с владельцем, параметрами и временем создания;
  состояние меняется DRAFT → PUBLISHED; создаётся запись журнала о публикации.

### Сценарий 2. Регистрация на мероприятие с ограниченным числом мест

- **Участники:** Participant (несколько), Organizer.
- **Начальное условие:** опубликованное мероприятие с N местами, мероприятие ещё не началось.
- **Основные действия:** участник просматривает список мероприятий и отправляет запрос на регистрацию; сервер атомарно
  проверяет состояние мероприятия, время начала, отсутствие у участника активной регистрации и наличие свободного места,
  затем создаёт регистрацию; когда места заканчиваются, следующие участники получают отказ «мест нет»; организатор
  запрашивает список участников своего мероприятия.
- **Результат:** зарегистрировано не более N участников, каждый видит свою регистрацию, организатор видит полный список.
- **Какие данные или состояние изменяются:** создаются регистрации в состоянии ACTIVE; уменьшается число свободных мест;
  создаются записи журнала.

### Сценарий 3. Отмена участия и отмена мероприятия

- **Участники:** Participant, Organizer.
- **Начальное условие:** у участника есть активная регистрация на опубликованное мероприятие, которое ещё не началось.
- **Основные действия:** участник отменяет свою регистрацию; место освобождается и становится доступно другим; позже
  организатор отменяет мероприятие; сервер в одной операции переводит мероприятие в CANCELLED и отменяет все оставшиеся
  активные регистрации.
- **Результат:** освобождённое место можно занять; после отмены мероприятия регистрация на него невозможна, все
  участники видят, что их регистрации отменены вместе с мероприятием.
- **Какие данные или состояние изменяются:** регистрации переходят ACTIVE → CANCELLED с указанием, кто и когда отменил;
  число свободных мест увеличивается; мероприятие переходит PUBLISHED → CANCELLED; создаются записи журнала.

## 6. Компоненты и внешние взаимодействия

Актуальная архитектура, потоки данных и границы доверия приведены в модели угроз (раздел 2).

Основные компоненты:

- HTTP-клиент отправляет учётные данные, команды и данные мероприятий в API.
- FastAPI проверяет структуру входа, аутентифицирует пользователя, проверяет роль и отношение пользователя к объекту (
  владелец мероприятия, владелец регистрации).
- Предметный слой применяет правила мероприятий и регистраций: переходы состояний, вместимость, сроки, единственность
  регистрации.
- Слой доступа к данным через SQLAlchemy читает и изменяет состояние в локальной SQLite-базе в рамках транзакций.
- API возвращает клиенту только поля, разрешённые для его роли и отношения к объекту (публичное представление,
  представление участника, представление организатора).

Главная граница доверия проходит между недоверенным HTTP-клиентом и API. Сервер не доверяет переданным клиентом
идентификаторам участника, владельца, роли, состояния и счётчика мест без собственной проверки.

## 8. Минимальное функциональное ядро

**Обязательные функции:**

- вход под заранее созданным учебным аккаунтом;
- роли Participant и Organizer;
- создание, редактирование и публикация мероприятия организатором;
- публичный просмотр опубликованных мероприятий с числом свободных мест;
- регистрация участника с атомарной проверкой вместимости;
- отмена участником собственной регистрации;
- отмена мероприятия организатором с отменой регистраций;
- просмотр организатором списка участников своего мероприятия;
- переходы DRAFT -> PUBLISHED -> CANCELLED и ACTIVE → CANCELLED для регистрации;
- серверная проверка роли, владельца, состояния, сроков и вместимости;
- постоянное хранение данных;
- воспроизводимый локальный запуск;
- автоматизированные позитивные и негативные тесты основных полномочий и правила вместимости.

**Функции, которые можно исключить при нехватке времени:**

- поиск и фильтрация мероприятий;
- пагинация списков;
- редактирование мероприятия после публикации (кроме отмены);
- просмотр расширенной истории действий;
- дополнительные поля мероприятия (категория, формат, теги).

После исключения этих функций сохраняются три сквозных сценария, различимые полномочия, значимые данные и собственная
серверная логика вместимости и регистрации.

## 9. Стек и путь к первой работающей версии

**Основные технологии:** Python 3.12+, FastAPI, Pydantic, SQLAlchemy, SQLite, pytest.
**Технологии, новые для команды:** не заявлены.
**Внешние сервисы, необходимые для запуска:** отсутствуют.
**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:** основные сценарии
полностью работают локально и не зависят от внешних сервисов.

**Реализованная техническая основа:** FastAPI-сервис с health-check, JWT-аутентификацией, ролями, сохраняемыми
мероприятиями и регистрациями, атомарной регистрацией с проверкой вместимости, командами публикации и отмены и журналом
действий. Все проектные данные сохраняются в локальном файле SQLite.

## 10. Локальный запуск

Для работы нужен Python 3.12 или новее. Отдельный сервер базы данных и другие внешние сервисы не требуются: приложение
использует локальную SQLite-базу.

### Linux и macOS

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
export JWT_SECRET='replace-with-at-least-32-random-characters'
export SEED_PASSWORD='replace-with-at-least-10-characters'
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

### Windows PowerShell

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
$env:JWT_SECRET = "replace-with-at-least-32-random-characters"
$env:SEED_PASSWORD = "replace-with-at-least-10-characters"
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Если PowerShell запрещает запуск `Activate.ps1`, для текущего окна можно выполнить
`Set-ExecutionPolicy -Scope Process RemoteSigned`, а затем повторить активацию окружения.

При первом запуске создаются файл `campus_events.db` и пять учебных аккаунтов. Пароль всех аккаунтов равен значению
`SEED_PASSWORD`.

| Email | Роль |
| --- | --- |
| `organizer1@campus.local`, `organizer2@campus.local` | Organizer |
| `participant1@campus.local`, `participant2@campus.local`, `participant3@campus.local` | Participant |

Аккаунты создаются только при создании новой базы. Если значение `SEED_PASSWORD` изменилось, уже существующие аккаунты
сохранят старый пароль. Для чистого учебного запуска можно удалить локальный `campus_events.db` и перезапустить приложение.

Без `JWT_SECRET` длиной не менее 32 символов и `SEED_PASSWORD` длиной не менее 10 символов приложение намеренно не
запускается. Секреты задаются через окружение и не должны сохраняться в Git.

После запуска доступны:

- health-check: [http://127.0.0.1:8000/health](http://127.0.0.1:8000/health);
- Swagger UI: [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs).

Токен можно получить через `POST /auth/login`, а затем вставить в Swagger UI через кнопку **Authorize**.

### Проверка

```bash
curl http://127.0.0.1:8000/health
python -m pytest
python scripts/demo.py
```

Автоматические тесты используют временную базу и не требуют запущенного сервера. Для `scripts/demo.py` сервер должен
работать, а в терминале с demo должно быть задано то же значение `SEED_PASSWORD`, с которым создавались учебные аккаунты.

Ожидаемый результат: health-check возвращает `{"status":"ok"}`, тесты завершаются успешно, demo выводит только `[PASS]`.

**Фактическая проверка 2026-10-06:** Python 3.13.3; приложение запущено через Uvicorn; `GET /health`
вернул `200 {"status":"ok"}`; `python -m pytest` — 29 passed и 100% покрытия строк и ветвей
приложения; `python scripts/demo.py` — 26/26 проверок PASS. Результат нужно повторить после фиксации оцениваемого commit
или tag `ek1`.

*Это подтверждение запуска, а не доказательство выполнения всех требований безопасности.*
